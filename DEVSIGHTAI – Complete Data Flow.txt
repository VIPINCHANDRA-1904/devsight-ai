Let's understand where every piece of data actually comes from.
1. First: There is a real application being monitored
Suppose a company has this application:
                    E-Commerce App
                          │
          ┌───────────────┼──────────────┐
          ↓               ↓              ↓
      User Service    Order Service   Payment Service
          │               │              │
          └───────────────┼──────────────┘
                          ↓
                       Database
DEVSIGHTAI doesn't generate these metrics itself.
It acts as a monitoring/analysis platform.
The application/server produces the data, and DEVSIGHTAI collects it.
2. How does it receive CPU and RAM?
For this, we can create a small Monitoring Agent.
For example:
Monitored Server
       │
       ↓
 DEVSIGHT Agent
       │
       ├── CPU
       ├── RAM
       ├── Disk
       ├── Network
       └── System information
       │
       ↓
 HTTP/HTTPS
       │
       ↓
 DEVSIGHTAI FastAPI
The agent can be a lightweight Python program running on the server.
For example, conceptually:
Every 10 seconds:

CPU       = 72%
RAM       = 64%
Disk      = 51%
Network   = 20 MB/s
Timestamp = 10:30:10
The agent sends this to your backend.
Example
{
  "server_id": "server-01",
  "timestamp": "2026-09-09T10:30:10",
  "cpu": 72,
  "memory": 64,
  "disk": 51
}
Your FastAPI backend receives this data.
3. How does it receive Response Time?
CPU and RAM are server-level metrics.
But response time belongs to the application/API.
For example:
User
 ↓
GET /api/payment
 ↓
Payment Service
 ↓
Database
 ↓
Response
Suppose the request takes:
Request started: 10:30:10
Response received: 10:30:11.8

Response time = 1.8 seconds
There are multiple ways to collect this.
For your project, the simplest is application instrumentation.
Your application sends:
{
  "service": "payment-service",
  "endpoint": "/api/payment",
  "response_time": 1.8,
  "status_code": 500,
  "timestamp": "2026-09-09T10:30:11"
}
DEVSIGHTAI receives it through an API.
4. How does it get Request Rate?
The application already knows how many requests it receives.
For example, during one minute:
10:00 – 1,200 requests
10:01 – 1,350 requests
10:02 – 1,480 requests
10:03 – 2,900 requests
The monitoring agent/application collector sends:
{
  "service": "payment-service",
  "requests_per_minute": 2900
}
DEVSIGHTAI stores this in the database.
5. How does it get Error Rate?
This can come from the application's HTTP responses/logs.
Suppose:
Total requests = 10,000
Failed requests = 850
Then:
Error Rate = 850 / 10000 × 100

           = 8.5%
The backend can calculate this itself from request events.
So you don't necessarily have to send error_rate directly.
You can send:
Request
Status Code
Timestamp
Service
and DEVSIGHTAI calculates:
Request Rate
Error Rate
Success Rate
This is actually a better architecture.
6. Now the important part: LOGS
Your professors may ask:

The DEVSIGHT Agent can monitor the application's log file.
For example:

8. How does it receive Deployment Information?
This is slightly different.
Deployment information doesn't come from CPU/RAM monitoring.
It comes from the CI/CD pipeline.
For example:
Developer
    ↓

    ↓

    ↓

    ↓
Testing
    ↓
Deployment
    ↓

After deployment, the CI/CD pipeline sends an event to DEVSIGHTAI.
For example:
{
  "service": "payment-service",
  "version": "2.4",
  "environment": "production",
  "deployed_at": "2026-09-09T10:20:00",
  "commit": "a82f91"
}
DEVSIGHTAI stores:
Payment Service
Version: 2.4
Deployment: 10:20 AM

13. But an anomaly alone isn't an incident
This is a very important distinction.
Suppose:
CPU = 95%
That doesn't automatically mean the application is broken.
Maybe someone is running a legitimate heavy process.
So DEVSIGHTAI should correlate multiple signals.
For example:
CPU ↑
RAM ↑
Latency ↑
Error Rate ↑
Database Timeout ↑
Deployment happened recently
Now the system has strong evidence that something is wrong.

16. AI produces the explanation
For example:

The Payment Service experienced database connection exhaustion shortly after version 2.4 was deployed.

Evidence

2. Review changes introduced in version 2.4.
3. Compare current database load with the previous version.
4. Consider rollback if the issue continues.

This aligns with your existing concept of AI-generated root-cause explanations, supporting evidence and actionable recommendations.

The key idea
DEVSIGHTAI does not magically receive everything from one source.
It receives different types of telemetry through different mechanisms:
Data	Source	How DEVSIGHTAI receives it
CPU	Server	Monitoring Agent
RAM	Server	Monitoring Agent
Disk	Server	Monitoring Agent
Response Time	Application/API	Application instrumentation
Request Count	Application/API	Application instrumentation
Error Rate	Application/API/logs	Events + log analysis
Logs	Application	Log Agent / API
Deployment	CI/CD	Webhook/API
Historical incidents	DEVSIGHTAI DB	PostgreSQL
User actions	Dashboard	React → FastAPI
